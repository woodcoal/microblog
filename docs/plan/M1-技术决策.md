## ADR-1：认证策略 — Cookie + Bearer 双模式

### 背景

SPEC 定义 JWT Token 通过 `Authorization: Bearer <token>` 认证。但 Astro SSR 页面在服务端渲染时需要识别用户身份（导航栏用户名、发帖按钮可见性等），纯 localStorage + Bearer header 方案在 SSR 场景下无法工作。

### 决策

JWT 同时存入两个位置：

| 存储方式     | 用途                | 属性                                      |
| ------------ | ------------------- | ----------------------------------------- |
| Cookie       | SSR 页面服务端读取  | HttpOnly, SameSite=Lax, Path=/            |
| localStorage | 客户端 API 请求携带 | 通过 `Authorization: Bearer <token>` 发送 |

认证逻辑：两者任一有效即视为已认证。

### 影响

- 登录 API 返回 token 后，前端同时写入 cookie 和 localStorage
- 登出时同时清除 cookie 和 localStorage
- SSR 页面通过 `Astro.cookies.get('token')` 读取用户身份
- API 路由优先读 `Authorization` header，fallback 到 cookie
- Cookie 不设 HttpOnly 以外的限制，确保 SSR 和客户端均可访问

### 后续注意

- M3 引入 API Token 时，API Token 仅通过 `Authorization` header 认证，不走 cookie
- CSRF 防护：SameSite=Lax 已提供基本防护，后续如需加强可增加 CSRF Token

## ADR-2：密码哈希库 — bcryptjs 替代 bcrypt

### 背景

`bcrypt` 依赖 Node.js native binding（C++ addon），Cloudflare Workers 运行时不支持 native addon，部署时会报错。

### 决策

使用 `bcryptjs`（纯 JavaScript 实现），API 与 `bcrypt` 完全一致，无需修改调用方式。

### 影响

- 性能略低于 native bcrypt，但 M1 阶段用户量极小，无影响
- 代码可直接在 Cloudflare Workers 运行，M4 部署无需重写

## ADR-3：JWT 库 — jose 替代 jsonwebtoken

### 背景

`jsonwebtoken` 依赖 Node.js `crypto` 模块，Cloudflare Workers 使用 Web Crypto API，不兼容。

### 决策

使用 `jose` 库，基于 Web Crypto API 实现，同时兼容 Node.js 和 Cloudflare Workers。

### 影响

- API 风格与 `jsonwebtoken` 不同，需注意用法差异
- `jose` 支持 HS256 签名，满足 SPEC 要求
- 代码可直接在 Cloudflare Workers 运行，M4 部署无需重写

## ADR-4：Astro 版本选择

### 背景

SPEC 指定 Astro 6.x，需确认当前最新稳定版本。

### 决策

使用当前最新稳定版。若 6.x 已正式发布则用 6.x，否则用 5.x。SSR 模式两者均支持，功能差异不影响开发。

### 影响

- 如使用 5.x，后续 6.x 发布后可平滑升级
- 核心依赖（`@astrojs/node`、`@astrojs/react`）版本需与 Astro 主版本匹配

## ADR-5：Markdown 渲染 — marked + 自定义 renderer

### 背景

SPEC 要求白名单 Markdown，仅支持粗体、斜体、删除线、行内代码、链接、换行，不支持标题、列表、引用、代码块、图片、表格等。

### 决策

使用 `marked` 库配合自定义 renderer：

1. 输入预处理：HTML 转义（防 XSS）
2. `marked` 解析：启用 GFM（支持删除线）
3. 自定义 renderer：仅输出允许的标签，其余转为纯文本
4. 禁用不支持的语法：标题、列表、引用、代码块、图片、表格

### 影响

- 渲染输出严格受控，无 XSS 风险
- 后续 M2 添加 @提及和 #标签解析时，在 marked 解析后做二次处理

## ADR-6：开发适配器 — Node.js（本地）+ Cloudflare（生产）

### 背景

Astro SSR 需要适配器（adapter），本地开发和 Cloudflare 部署使用不同适配器。

### 决策

- M1-M3 开发阶段：使用 `@astrojs/node` adapter
- M4 部署阶段：切换到 `@astrojs/cloudflare` adapter

### 影响

- `astro.config.mjs` 中 adapter 配置需通过环境变量切换
- 本地开发使用 SQLite，Cloudflare 使用 D1，通过 Prisma 切换
- 文件存储本地使用文件系统，Cloudflare 使用 R2，通过环境变量切换

## ADR-7：Prisma 7 + libsql adapter

### 背景

SPEC 指定 Prisma 6.x，但当前最新版为 7.x。按"使用最新版本"原则升级到 Prisma 7。Prisma 7 有重大架构变更：

- `schema.prisma` 中不再包含 `url`，数据库连接移至 `prisma.config.ts`
- PrismaClient 必须通过 driver adapter 连接数据库
- 不再自动加载 `.env` 文件，需手动引入 dotenv

同时，`better-sqlite3` 需要 C++ 编译环境（Windows 上需 Visual Studio C++ 工具集），开发环境不友好。

### 决策

1. 使用 Prisma 7.x + `prisma.config.ts` 配置文件
2. 使用 `@prisma/adapter-libsql`（纯 JS，无需编译）替代 `better-sqlite3`
3. schema.prisma 中 generator provider 改为 `prisma-client`（Prisma 7 新名称）
4. 输出目录设为 `../generated/prisma`，代码中从此路径导入

### 影响

- libsql 与 Cloudflare D1 兼容，M4 部署无需切换 adapter
- 无需 C++ 编译环境，Windows/macOS/Linux 均可开发
- PrismaClient 导入路径从 `@prisma/client` 改为 `../../generated/prisma/client`
- seed 脚本使用 tsx 运行（支持 ESM + TypeScript）

## ADR-8：公共函数库

### 背景

多个页面和组件需要使用相同的工具函数（如时间格式化、API 响应封装），如果每个文件各自定义会导致重复代码和维护困难。

### 决策

创建 `src/lib/utils.ts` 作为公共函数库，所有通用工具函数统一存放于此。

当前包含：

- `formatRelativeTime()`：相对时间格式化
- `successResponse()`：标准化成功响应
- `errorResponse()`：标准化错误响应

### 影响

- 新增通用函数时统一添加到 utils.ts
- 页面和组件通过 `import { xxx } from '@/lib/utils'` 引用

## ADR-9：站点配置从数据库迁移到 .env

### 背景

原设计使用 SiteSettings 数据库模型存储站点配置（标题、描述、注册开关等），通过管理后台 API 动态修改。但对于轻量级微博系统：

- 站点配置修改频率极低（部署时确定，几乎不变）
- 数据库存储增加了每次请求的查询开销（BaseLayout 每页都读 SiteSettings）
- 管理后台 API 增加了代码复杂度和安全攻击面
- Cloudflare Workers 环境下 .env 变量是标准配置方式

### 决策

1. 删除 SiteSettings 数据库模型
2. 所有站点配置迁移到 .env 环境变量
3. 删除 GET /api/site/settings 和 PUT /api/admin/site/settings API
4. 删除 /admin/site 页面路由
5. 通过 src/lib/config.ts 统一读取环境变量，提供类型安全的配置常量

### 影响

- 修改站点配置需要编辑 .env 文件并重启服务
- 不再需要管理后台的"网站设置"页面
- 每个页面渲染不再需要查询数据库获取配置
- 配置与代码一起版本控制，便于追踪变更
