# MT-112 媒体附件与后台审计技术方案

> 关联任务：MT-111、MT-112  
> 状态：可实施基线  
> 更新日期：2026-08-08

## 1. 结论

本次沿用 `Post -> Media -> FileStorage`，不另建缩略图或附件文件表：

- `FileStorage` 继续表示去重后的物理文件；`Media` 表示文件被某篇帖子引用。
- `Media.slot = "thumbnail"` 表示文章缩略图，其余媒体保持 `slot = null`。在 `Media(postId, slot)` 上建立唯一约束，利用 SQLite 与 MySQL 均允许唯一索引中存在多个 `NULL` 的行为，实现“每篇帖子至多一张缩略图”，同时不限制正文图片和附件数量。
- 附件继续由 `Media.fileType = "attachment"` 区分，缩略图必须同时满足 `fileType = "image"`。列表只读缩略图，详情另读附件；缩略图不混入正文图片画廊。
- 所有后台处置统一进入 `AdminAuditLog + AdminAuditTarget`。业务状态更新、受影响目标明细和审计主记录必须在同一个 Prisma 事务中提交；任何一步失败均整体回滚。
- 管理后台继续使用 Astro Actions，不把审计查询暴露到 `/api/v1` 或 Agent API。所有写 Action 与 Service 都强制验证理由，界面校验只负责体验。

这是一份接口与数据约束基线，不在本任务中实现大规模业务代码。

## 2. 当前事实与缺口

### 2.1 媒体现状

- `prisma/schema.sqlite.prisma` 与 `prisma/schema.mysql.prisma` 已有 `FileStorage`、`Media`，并由 `Post.media` 关联。
- `src/lib/upload.ts` 已限定图片为 jpg/jpeg/png/gif/webp、单文件 5 MiB、每帖最多 9 张；附件支持 pdf/zip/Office/txt/csv/rar/7z，单文件 20 MiB，但没有每帖附件数量和总大小限制。
- 字段名 `md5Hash` 实际保存 SHA-256。此次只新增能力，不改名；改名需独立兼容迁移。
- `saveFile()` 在上传时立即增加 `refCount`，帖子绑定时不增加；未提交或取消编辑的上传会永久占用引用。
- `deleteFileRef()` 的数据库更新、物理文件删除和 `FileStorage` 删除不在同一事务内，并发及物理删除失败时可能留下不一致记录。
- `src/pages/uploads/[...path].ts` 按路径公开返回所有文件并设置长期公开缓存，没有帖子可见性或登录校验。附件若继续返回该 URL，会绕过文章权限。
- `src/services/content.service.ts` 的创建/编辑已经以 `mediaIds` 维护媒体集合及版本快照，可作为扩展入口；`PostRevision.mediaSnapshot` 不能因本次改造失效。
- 博客列表通过 `POST_CARD_INCLUDE` 读取媒体，详情与 `/api/v1` 也会读取全部媒体；当前 DTO 未区分缩略图、正文图片和附件。

### 2.2 后台处置现状

- `src/actions/admin.ts` 每个 Action 均检查管理员身份，这是应继续复用的鉴权边界。
- `src/services/admin.service.ts` 保留单次最多 100 条的批量上限。
- 帖子删除、恢复、锁定要求理由；解锁、置顶、取消置顶不要求理由。用户启用/禁用及评论删除也没有理由参数。
- 帖子表中的 `deleteReason`、`lockReason` 等字段只保存“当前状态附属信息”，无法表达完整历史、批量操作和所有目标类型。
- `ActivityLog` 面向站内动态，不包含理由、批次、结果及管理员处置的完整目标，不能替代审计表。
- 用户、帖子、评论的 `updateMany` 与审计记录目前没有共同事务，因此不能满足“处置成功与审计记录不半成功”。

## 3. 数据模型

### 3.1 媒体模型增量

两个 Prisma schema 同步新增：

```prisma
model Media {
  // 既有字段省略
  slot String? // null=普通正文媒体/附件，thumbnail=文章缩略图

  @@unique([postId, slot])
  @@index([postId, fileType, sortOrder])
}
```

约束：

1. 只有 `Post.mode = "blog"` 可设置 `slot = "thumbnail"`。
2. `slot = "thumbnail"` 时 `fileType` 和对应 `FileStorage.fileType` 必须均为 `image`。
3. 同一 `FileStorage` 可被多篇帖子引用；每个 `Media` 行计一个引用。
4. 正文图片和附件的 `slot` 均为 `null`；它们通过 `fileType` 区分。不要使用 `isThumbnail + @@unique([postId, isThumbnail])`，否则普通媒体也会被错误限制为一条。
5. `originalName` 对附件必填且使用上传时的原名；展示时转义，下载响应使用 RFC 5987 编码，不把它拼入磁盘路径。

迁移中的既有 `Media` 全部保持 `slot = null`，不回填或猜测缩略图，因此不会改变现有帖子版本快照。

### 3.2 审计模型

两个 schema 同步新增以下等价模型；字符串枚举由 TypeScript 常量与 Service 校验，避免双数据库迁移产生不同枚举语义。

```prisma
model AdminAuditLog {
  id             String   @id @default(cuid())
  operatorId     String
  requestId      String
  targetType     String   // user | post | comment
  action         String   // user.disable、post.lock 等
  reason         String
  result         String   @default("success")
  requestedCount Int
  affectedCount  Int
  createdAt      DateTime @default(now())

  operator User               @relation(fields: [operatorId], references: [id], onDelete: Restrict)
  targets  AdminAuditTarget[]

  @@unique([operatorId, requestId])
  @@index([createdAt, id])
  @@index([operatorId, createdAt, id])
  @@index([targetType, action, createdAt, id])
}

model AdminAuditTarget {
  id         String @id @default(cuid())
  auditLogId String
  targetId   String
  outcome    String @default("updated") // updated | unchanged

  auditLog AdminAuditLog @relation(fields: [auditLogId], references: [id], onDelete: Restrict)

  @@unique([auditLogId, targetId])
  @@index([targetId, auditLogId])
}
```

同时为 `User` 增加 `adminAuditLogs AdminAuditLog[]` 关系。

审计表不保存用户邮箱、正文、评论内容、密码、令牌、附件路径、请求头或任意请求体快照。目标页面需要展示名称时，通过目标 ID 做受限查询；目标已不存在时只显示 ID。`reason` 是管理员输入，长度限制 2～500 字符，展示时按纯文本转义。

不可变性采用双层约束：

- 应用层只导出创建和查询函数，不提供 update/delete；`onDelete: Restrict` 禁止级联擦除操作者和审计明细。
- SQLite 与 MySQL 迁移分别创建阻止 `UPDATE`、`DELETE` 的触发器。迁移回滚可显式删除触发器；日常应用账号不绕过触发器。

`result` 首期只写 `success`。失败尝试进入结构化应用日志，不在业务事务失败后另写“成功审计”，避免误导；如产品未来要求记录失败尝试，应另设安全事件流水，而非放宽本表事务约束。

## 4. 写入契约

### 4.1 博客创建与编辑

在现有 `createPost` / `updatePost` 输入中增加：

```ts
interface BlogAssetInput {
	thumbnailFileStorageId?: string | null;
	attachmentFileStorageIds?: string[];
}
```

语义：

- 创建：缺省或 `null` 表示没有缩略图；附件缺省等价于空数组。
- 编辑：`thumbnailFileStorageId === undefined` 表示保持，`null` 表示移除，字符串表示替换；`attachmentFileStorageIds === undefined` 表示保持，数组表示按给定顺序全量替换。
- `mediaIds` 继续只表达现有正文媒体，保持旧调用方兼容。
- 所有 ID 先去重并整批查询；只要有不存在、类型不符或越权文件，整个请求失败。
- 帖子、Media diff、`PostRevision` 快照和数据库引用计数在同一事务中完成。

建议将 `PostRevision.mediaSnapshot` 从旧的 ID 数组兼容升级为版本化 JSON：

```json
{
	"version": 2,
	"bodyMediaIds": ["..."],
	"thumbnailMediaId": "...",
	"attachmentMediaIds": ["..."]
}
```

读取版本历史时同时兼容旧数组（视为 `bodyMediaIds`）和 v2 对象。版本快照只记录 Media/FileStorage 标识，不复制物理文件。

### 4.2 上传暂存与引用计数

不得再把“成功上传”永久等同于“帖子已引用”。实施时增加轻量 `UploadReservation`（上传者、`fileStorageId`、原始文件名、类型、过期时间、消费时间），或提供等价的有期限上传凭证：

1. 上传写入/复用 `FileStorage`，创建归属于当前用户的 reservation，并返回 reservation ID 与预览 URL。
2. 创建/编辑帖子只消费当前用户未过期的 reservation；不能用猜到的 `FileStorage.id` 绑定他人上传。
3. reservation 转为 `Media` 时引用所有权转移，不重复加一。
4. 取消编辑或 reservation 过期时释放引用。首期可在上传、发帖与维护命令中机会式清理，不引入队列依赖。
5. 删除 `Media` 时在事务中递减引用；归零只把文件标记为待删除。事务提交后删除物理文件，失败则由幂等清理命令重试，不能先删物理文件再提交数据库。

对同一哈希的复用还必须验证已存记录的 `fileType` 与实际上传用途一致。当前 `md5Hash` 字段实际是 SHA-256，应在注释和文档中明确，独立任务再考虑无停机改名。

### 4.3 后台处置

所有动作统一输入：

```ts
type AdminMutationInput = {
	ids: string[]; // 去重后 1..100
	reason: string; // trim 后 2..500，所有动作必填
	requestId: string; // UUID，同一操作者下幂等
};
```

覆盖动作：

| targetType | action                         | 状态变化                              |
| ---------- | ------------------------------ | ------------------------------------- |
| user       | `user.disable` / `user.enable` | `isDisabled` 切换；禁用继续排除 admin |
| post       | `post.delete` / `post.restore` | 软删除/恢复                           |
| post       | `post.lock` / `post.unlock`    | 锁定/解锁                             |
| post       | `post.pin` / `post.unpin`      | 全局置顶/取消置顶                     |
| comment    | `comment.delete`               | 软删除                                |

一致性算法：

1. Action 鉴权管理员，并用 Zod 校验 `ids/reason/requestId`；Service 再执行相同业务边界校验，防止未来非 Action 调用绕过。
2. 开启 Prisma 事务，先按动作的状态谓词查询实际候选 ID。
3. 执行带相同谓词的 `updateMany`；若返回数量与候选数不一致，抛错回滚，避免并发下审计目标与实际状态不符。
4. 创建一条 `AdminAuditLog`，再为所有请求目标创建 `AdminAuditTarget`。实际改变的目标为 `updated`，合法但状态已一致的目标为 `unchanged`；不存在或不允许的目标按严格模式令整个请求失败。
5. 唯一键 `(operatorId, requestId)` 命中时返回既有 `affectedCount`，不重复执行和不重复审计。

不允许 Service 先调用现有 `src/lib/post.ts` / `comment.ts` / `user.ts` 的全局 Prisma 更新函数再补审计。应新增接收 `Prisma.TransactionClient` 的内部 mutation 函数，由统一的 `executeAuditedAdminMutation()` 编排。

## 5. 读取与下载契约

### 5.1 列表和详情 DTO

内部页面与 `/api/v1` 的公共 DTO 采用同一形状：

```ts
type MediaDto = {
	id: string;
	url: string;
	mimeType: string;
	size: number;
};

type AttachmentDto = MediaDto & {
	originalName: string;
	downloadUrl: string;
};

type PostSummaryDto = {
	// 既有字段
	thumbnail: MediaDto | null;
};

type PostDetailDto = PostSummaryDto & {
	// 既有字段
	bodyMedia: MediaDto[];
	attachments: AttachmentDto[];
};
```

- 博客列表页 `src/pages/blog/index.astro`、分类页和 `BlogArticleList.astro` 只 select `slot = thumbnail` 所需字段，避免加载全部附件。
- 博客详情、编辑回显和 v1 详情按 `slot/fileType/sortOrder` 拆分；现有 `media` 字段在兼容期继续表示正文媒体，不把缩略图重复塞入数组。
- 受限文章列表仍可返回标题和缩略图字段，但只有可见性检查通过时才返回可读取 URL；否则 `thumbnail = null`，避免通过图片泄露内容。

### 5.2 下载路由

新增 `GET /media/:mediaId/download`，不得把 `FileStorage.filePath` 当作附件 API：

1. 以 Media ID 查询帖子、文件和必要的作者/可见性字段。
2. 复用 `checkPostVisibility()`；删除帖子仅作者或管理员可下载，普通访客得到 404，避免探测资源存在。
3. 附件响应使用 `Content-Disposition: attachment; filename*=UTF-8''...`、数据库中的 MIME、`X-Content-Type-Options: nosniff`。
4. 私有或受限资源使用 `Cache-Control: private, no-store`；公开附件可使用短期私有缓存，但首期不做公开永久缓存。
5. 路由仅接受 Media ID，不接受任意磁盘路径；保留并强化路径规范化和真实路径必须位于 `UPLOAD_DIR` 内的校验。
6. `HEAD` 与 `GET` 执行同一权限判断。若实现 Range 下载，必须单独测试边界；首期可不支持。

现有 `/uploads/*` 对所有媒体公开是已存在的权限缺口。为避免一次性破坏正文图片 URL，实施顺序是先让新附件和缩略图只返回受控 Media URL，再迁移旧图片引用；不得为新附件继续生成公开 `/uploads/attachments/...` 链接。

## 6. 审计查询

新增管理员专用 `queryAdminAuditLogs` Astro Action 与 `/admin/audit` 页面，并在 `src/layouts/Admin.astro` 的“内容治理”组增加入口。

Action 输入：

```ts
{
  targetType?: 'user' | 'post' | 'comment';
  action?: AdminAuditAction;
  operatorId?: string;
  result?: 'success';
  from?: string;       // ISO 8601
  to?: string;         // ISO 8601，服务端约束最大查询跨度
  targetId?: string;
  cursor?: { createdAt: string; id: string };
  limit?: number;      // 默认 20，最大 100
}
```

输出 `{ items, nextCursor }`，按 `(createdAt DESC, id DESC)` 游标分页。每项只返回操作者公开标识、动作、纯文本理由、时间、requested/affected 计数以及当前页需要的目标 ID/outcome；不返回目标正文和敏感字段。

权限在 Action 和 Service 两层强制管理员身份；页面 SSR 同样由 `AdminLayout` 保护。不要加入公开 `/api/v1` OpenAPI。针对 `targetId` 的筛选从 `AdminAuditTarget(targetId, auditLogId)` 索引反查，其他筛选使用第 3.2 节索引。

## 8. 实施拆分与依赖

### 阶段 1：服务端契约与数据库（先行，不能派给纯前端角色）

适合熟悉 TypeScript、Prisma、Astro 服务端和双数据库迁移的全栈/后端开发者：

1. 同步修改两个 schema，生成 SQLite/MySQL 迁移及不可变触发器。
2. 实现上传 reservation、媒体事务与受控下载路由。
3. 实现统一审计执行器、全部后台动作理由校验和审计查询 Service/Action。
4. 更新 DTO 与服务端选择字段，提供稳定类型给 UI。

阶段 1 完成并以测试固定 Action/DTO 后，前端才可并行接入。

### 阶段 2A：博客 UI（花荣）

花荣负责 Astro/React 浏览器界面，不负责数据库事务或服务端审计：

- 博客新建/编辑页的单张缩略图选择、预览、替换、移除。
- 附件选择、上传进度、数量/大小提示、排序与删除。
- 列表缩略图、详情附件下载入口、键盘和读屏语义。
- 只消费阶段 1 固定的 Action/DTO，不在浏览器复制权限和审计规则。

### 阶段 2B：后台 UI（花荣，可与 2A 并行）

- 用户、帖子、评论所有单项/批量动作统一理由对话框。
- 生成并复用一次 `requestId`，失败重试不换 ID。
- 新增审计查询页的筛选、游标翻页和空态。

### 阶段 3：QA 与安全回归

在 1、2A、2B 全部完成后执行双 provider 集成测试、浏览器验收和升级回滚测试。产品经理可据此创建三个实施 issue（服务端、两组 UI）和一个 QA issue；阶段 2 的两个 UI issue 可并行，均依赖阶段 1。

## 9. 测试清单

### 数据库与媒体

- SQLite、MySQL 均能从现有基线迁移；已有 Media 保持可读。
- 同一帖子第二个 `thumbnail` 写入被唯一约束拒绝；多个 `slot = null` 正常。
- 非 blog、非图片、越权或已过期 reservation 不能设为缩略图。
- 创建、替换、移除缩略图和附件后，Media、快照及引用计数一致。
- 同内容重复上传、取消编辑、过期清理、并发移除不会出现负引用或误删共享文件。
- v1 旧 `media` 契约不混入缩略图；列表不加载附件正文。

### 下载与权限

- public、logged_in、followers、following、private、users、password 各可见性分支与正文读取一致。
- 未授权、已删除、无效 Media 均不泄露文件存在性；附件响应头安全且文件名编码正确。
- 路径穿越、双编码、符号链接逃逸及错误 MIME 不能读取 `UPLOAD_DIR` 外文件。

### 后台审计

- 普通用户和未登录用户不能调用写入或审计查询 Action。
- 九类处置动作缺理由、纯空白、超长、空 IDs、超过 100 条均由服务端拒绝。
- 状态更新成功时恰有一条审计主记录和完整目标明细；模拟审计插入失败时业务状态回滚。
- 重复 `requestId` 不重复执行；并发状态变化导致候选数不一致时整体回滚。
- `UPDATE/DELETE AdminAuditLog/AdminAuditTarget` 在两个数据库中均被触发器拒绝。
- 筛选、复合游标、同时间戳稳定排序和最大 limit 正确；结果不含邮箱、正文、评论内容及文件路径。
- `tests/admin-authorization.acceptance.test.ts` 加入 `/admin/audit`，继续覆盖未登录/普通用户/管理员三态。

## 11. 风险与禁止事项

- 不能只给 UI 增加必填框；所有 Action/Service 必须拒绝空理由。
- 不能继续用公开 `/uploads` 地址交付新附件，否则文章权限形同虚设。
- 不能用 `ActivityLog` 冒充管理员审计，也不能只在帖子当前字段中保存最后一次理由。
- 不能在业务事务提交后“尽力补写”审计；这会产生不可修复的半成功。
- 不能同时独立修改 SQLite/MySQL schema 而不做结构对照和双迁移测试。
- `FileStorage.refCount` 与物理文件删除涉及现存技术债，应随媒体实施一起收口；只增加 UI 会放大泄漏。
